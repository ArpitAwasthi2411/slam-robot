# Repo review, October 2026 (Phase 0)

Scope: firmware (3 sketches), ROS package (nodes + pure-Python logic), launch/config, the app and the classic
page, scripts, tools, docs and CI. Method: read the core modules (navigator_core, esp32_bridge, dashboard,
dashboard_server, auth, navigator, explain, mapsave, mcp_server), automated checks over everything
(pyflakes on all Python, `bash -n` + shellcheck on all scripts, YAML params vs. the parameters each node
declares/reads, every API path and navigator request type used by each client vs. what the server/core
implements, firmware `#define` pins vs. every pin table in the docs, test coverage per module), and ran the
tools (`dashboard_sim.py`, `eval_nav.py`, `eval_commands.py`, the MCP server against the simulator).

Tests: 112 → **126** (125 + 1 skip under the CI's Python 3.10 / pytest 6.2.5). Coverage of the pure-Python
logic 65 % → 71 %. The four ROS node wrappers (navigator, dashboard, goal_controller, us_listener) have no
unit tests: they are thin and need TF/rclpy; the bridge is covered end to end over a pseudo-terminal.

## Bugs fixed

| # | Where | What was wrong | Fix + test |
|---|---|---|---|
| 1 | `dashboard_server.py`, `dashboard.py`, `esp32_bridge.py` | `POST /api/cmd {"v": "nan"}` passed `float('nan')` through the `min/max` clamp (NaN compares false) into `/cmd_vel_teleop`. In the bridge's 20 Hz timer `format_velocity` does `int(round(nan))` → `ValueError` inside an rclpy timer, which can take the bridge (motor link) down. Same for `inf` on the angular part and for `/api/goal`. | HTTP: `_num()` rejects non-finite numbers with 400. Dashboard: `command()` ignores non-finite. Bridge: `_on_cmd` drops non-finite twists from **any** publisher. `test_http_rejects_non_finite_drive_and_goal`, `test_non_finite_command_is_ignored_and_timer_survives` |
| 2 | `navigator_core._command` | The "stop" command cancelled missions but left **Map by itself** running: 2 s later the explorer queued a new frontier and the robot drove off again. | "stop" also ends exploration. `test_stop_command_also_ends_exploration` |
| 3 | `navigator_core._maybe_auto_home` | `_go_home` can raise (`battery critical`) inside `step()`; the node turns any exception from `step()` into an INTERNAL mission failure every tick. | caught + logged. `test_auto_home_never_crashes_the_loop` |
| 4 | `explain.py` | A failure code without a template (e.g. the node's `INTERNAL`) put the raw text through `str.format()`: any `{` in an exception message (dict/KeyError reprs) crashed "why did you stop?". | raw text is used as is. `test_explain_failure_text_with_braces` |
| 5 | `scripts/setup_ports.sh` | Written for two USB devices. With the ESP32-S3 on the GPIO UART (v2.6) step 2 waits for an ESP32 USB device that never comes, and the rules file it writes competes with `98-esp32-uart.rules` for `/dev/esp32`. | UART mode: if `98-esp32-uart.rules` exists (or `ESP32_LINK=uart`) it only names the LiDAR and never writes an esp32 USB rule. |
| 6 | `tools/serial_probe.py` | Speeds computed with `TICKS_PER_REV = 4740`; the firmware and `robot_params.yaml` use ~4970 (measured): every mm/s it printed was ~5 % high. It also told you to edit the legacy sketch. | 4970; points to `robot_esp32s3` / `robot_esp32_classic`. |
| 7a | `tools/dashboard_sim.py` | The simulator resets its data in the repo's `maps/` folder at every start, so running it from a test deleted the tracked `maps/sim/schedules.json`. | `SimBackend(data_dir=...)`; tests use a temporary folder (the CLI keeps the old default). |
| 7 | `deploy/docker/entrypoint.sh` | Malformed shellcheck directive (comment text on the directive line; shellcheck error SC1125). | directive on its own line. |
